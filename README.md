# llmb-bringup

Automated bring-up validation for NVIDIA GPU clusters, driven by
**`llmb-run`** (NVIDIA DGX Cloud Benchmarking).

Per-node hardware health checks gate per-rack fabric and training checks. One
head-node orchestrator submits exactly one `llmb-run` job per NVLink domain,
scores the results, drains what fails, and keeps a per-rack matrix you can read
on a bring-up call.

**Nothing in this repo is specific to a cluster, customer, GPU model or site.**
All site facts come from `conf/cluster.conf`, which is generated by an interview
script that detects most of it for you:

```bash
git clone <this repo> /opt/llmb-bringup && cd /opt/llmb-bringup
bin/interview.sh              # detects, asks, writes conf/cluster.conf + inventory
bin/verify-cluster.sh         # checks every answer against the live cluster
bin/rack-orchestrator.sh --dry-run
```

Ported from an sbatch/Slurm bring-up suite; see [MIGRATION.md](MIGRATION.md) for
the command mapping and the bugs offline validation caught.

**Validated on real hardware.** The suite has been run end to end against a live
GB300 NVL72 cluster — a full 72-GPU NCCL sweep through `llmb-run submit`, with
the measured bandwidth recorded next to the profile floors it is scored against.
See [VALIDATION-NscaleTX-2026-07-29.md](VALIDATION-NscaleTX-2026-07-29.md) for
the numbers, the container environment gotchas that cost real debugging time
(§11.1 below), and the audit trail for "does this repo modify `llmb-run`?".

### Does this repo modify `llmb-run`? No.

The first question every site team asks, so it is answered up front and is
verifiable from the tree. `lib/llmb.sh` is the only file that knows how to talk
to `llmb-run`; it **invokes** the CLI and never writes into `$LLMB_INSTALL` or
the `dgxc-benchmarking` checkout. Recipes, `metadata.yaml`, the container and
`llmb-run` itself are stock. What changed is the *caller*: `sbatch
jobs/allreduce.sbatch` became `llmb-run submit -w microbenchmark_nccl …`.

## 1. What it does

```
              ┌─ per node, event driven ──────────────────────────────────┐
  node boots  │ node_health.sh   ~38 hardware/software checks vs a golden  │
              │                  baseline -> Slurm IDLE, or DOWN + reason  │
              │ launch_job.sh    node-scope sbatch work (GPU diagnostics)  │
              └───────────────────────────────────────────────────────────┘
                                    │  results/<node>/dcgm.txt = DONE
                                    v
  ┌─ head node, every 5 min (systemd timer or cron) ───────────────────────┐
  │ rack-orchestrator.sh                                                   │
  │   collect: poll in-flight jobs -> score -> DONE/FAIL -> drain          │
  │   submit : for each rack whose gates are met and whose nodes are all    │
  │            idle, submit ONE llmb-run job                               │
  └────────────────────────────────────────────────────────────────────────┘
                                    │
        llmb-run submit -w microbenchmark_nccl --scale <rack GPUs>
                     --force --nodelist <the rack>
```

Verdicts fan back out to `results/<node>/<workload>.txt` with `DONE` or `FAIL` as
the last line, so anything that already consumed that format keeps working.

### Why rack-scale work runs from the head node

An `llmb-run` workload occupies every node of an NVLink domain. If it were
submitted by a per-node hook, all 18 nodes of a rack would each submit the same
18-node job. Rack-scale work must be submitted once per rack, from one place.
Per-node health checking stays on the node.

## 2. Prerequisites

### Head node

| Requirement | Check |
|---|---|
| bash ≥ 4 (associative arrays) | `bash --version` |
| `flock`, `awk`, `sed`, `grep`, `find` | `command -v flock awk` |
| Slurm client tools | `sinfo squeue sacct scontrol scancel sbatch` |
| Slurm accounting working | `sacct -n -X -o State -j 1` |
| A service account (not root) | any; the interview asks |
| Shared filesystem readable by all nodes | for `$LLMB_INSTALL` |
| Node-local scratch (e.g. `/raid`) | container staging; optional but strongly advised |
| optional `clush` / `pdsh` | faster image staging |
| optional `dshbak` | grouped `status-check.sh` output |
| optional `cmsh` (BCM) | event-driven node health; cron works otherwise |

`sacct` matters more than it looks. Without it, job state comes from `squeue`
only, which forgets a job the moment it finishes — every completed rack job then
looks like "unknown to slurm" and gets retried.

### Not required

A specific cluster manager, GPU model, node naming scheme, rack size, or
partition name. All of that is discovered or asked.

### Python

Only `llmb-run` needs Python (3.12, in its own venv built by its installer). This
suite is pure bash + awk at runtime; `docs/gen-inventory.py` is an optional
one-off for sites that keep a node workbook.

## 3. Installing llmb-run

Once per cluster, on a **shared filesystem** every node can read.

```bash
cd /shared
git clone --branch <release> https://github.com/NVIDIA/dgxc-benchmarking.git
cd dgxc-benchmarking
./install.sh
```

The installer builds a Python 3.12 venv, installs `llmb-run` and `llmb-install`,
then prompts. Answers that matter:

| Prompt | Guidance |
|---|---|
| Installation path | a **shared** path — becomes `$LLMB_INSTALL` |
| SLURM account / partition | your GPU partition |
| GPU type | your GPU model (e.g. `GB300`) |
| CPU architecture | `arm64` for Grace-based nodes, `x86_64` otherwise — check `uname -m` on a compute node, not the head node |
| Installation method | `SLURM` |
| Workload | `Custom` → select at minimum **`microbenchmark_nccl`** and one pretrain workload (e.g. `pretrain_nemotron-h`) |
| HuggingFace token | usually blank |

It imports the container through Slurm. If that srun fails on
`--gpus-per-node=8` on a 4-GPU node, that default does not match your hardware —
import the container by hand with the right value.

Then:

```bash
export LLMB_INSTALL=/shared/llmb          # persist in your profile
llmb-run list                             # must list the workloads you selected
```

### Confirm the release — this decides whether the suite can work

```bash
llmb-run --help | grep -E '\b(submit|single)\b'
llmb-run jobs --help >/dev/null 2>&1 && echo "jobs: yes" || echo "jobs: no"
```

| Release era | Launch verb | Placement flags | `jobs` subcommand | Usable |
|---|---|---|---|---|
| newer | `submit` | `--nodelist`, `--exclude`, `--force`, `--proxy` | yes | **yes — required** |
| older | `single` | none | no | degraded |

With `single` only, a rack-scale job **cannot be pinned to a rack**. The
orchestrator refuses to submit rather than queue a job whose result cannot be
attributed to a rack — that would corrupt the matrix. Override with
`AAT_ALLOW_UNPINNED=1` only if you accept unattributable results.

Without `jobs`, TFLOPS/GPU is unreadable and pretrain workloads fail with
`no TFLOPS/GPU reported`. Upgrade, or set `metric=-` on that workload.

### Why `--force` is not optional

A rack is rarely a power of two. An 18-tray GB300 NVL72 rack is **72 GPUs**, and
upstream `nccl/metadata.yaml` for `gb300` ships a scale whitelist of
`[4, 8, 16, 32, 64, 128, 256, …]` — 72 is not in it, so a plain submit is
**rejected outright**.

`conf/workloads.conf` sets `scale_flag=force` on every rack- and group-scope
workload, which becomes `llmb-run --force` and bypasses the whitelist *without
touching upstream recipe data*. This is the supported way to do it. Site tooling
that instead patches `metadata.yaml` will have the edit silently reverted by the
installer's `git checkout -f` on its next run, and the job will start failing
again weeks later with no obvious cause.

If your rack size happens to be a whitelisted scale you can set
`scale_flag=-`, but there is no reason to.

### Prove one job by hand before automating

```bash
llmb-run submit -w microbenchmark_nccl -s nccl --dtype fp8 \
         --scale <gpus_in_one_rack> --force --nodelist '<one rack>'
squeue -u "$USER"
```

Results land under
`$LLMB_INSTALL/workloads/microbenchmark_nccl/experiments/*_<jobid>/LOG_*/`.
**`llmb-run` does not parse NCCL results** — that is why this repo ships its own
busbw parser.

## 4. Step 1 — the interview

```bash
bin/interview.sh
```

It detects what it can and asks about the rest, with the detected value as the
default for every question:

| Section | Detected from |
|---|---|
| cluster name | `scontrol show config` → `ClusterName` |
| platform profile | `nvidia-smi` GPU model, mapped to `conf/profiles/` |
| partition, account | `sinfo` default partition, `sacctmgr` |
| GPUs per node | `sinfo -o %G` gres string |
| topology mode | `scontrol show config` → `TopologyPlugin` |
| **rack layout** | node list from `sinfo`, then candidate grouping rules scored for uniformity |
| llmb-run venv / install / release / image | filesystem probe + `llmb-run --help` |
| fabric interface | `srun` on one node, highest-speed non-IB link |
| node health driver | `cmsh` present → BCM, else cron/none |

The rack-layout step is the interesting one. It proposes several sed rules for
turning a node name into a rack id and shows what each produces:

```
  candidate rule                        racks trays/rack verdict
  ----------------------------------    ----- ---------- -------
  s/-[0-9]\+$//                           112         18 uniform, matches profile
  s/[0-9]\+$//                              7        288 mixed sizes
  s/-[^-]*-[^-]*$//                         1       2016 mixed sizes
```

Pick one, or type your own. It then previews the first rack, flags any rack whose
node count differs from the rest, and writes the inventory.

Outputs:

| File | Purpose |
|---|---|
| `conf/cluster.conf` | the site configuration the suite reads |
| `conf/inventory/racks.txt` | rack → node mapping |
| `conf/interview-answers.conf` | every answer, replayable |

Other modes:

```bash
bin/interview.sh --non-interactive     # accept every detected value
bin/interview.sh --offline             # no cluster access; prompts for everything
bin/interview.sh --answers conf/interview-answers.conf --force   # replay
```

The answers file makes a second cluster a two-minute job: copy it, edit the few
values that differ, replay.

### The rack inventory is the authority

Node numbering inside a rack is frequently **not contiguous** — real clusters
have racks whose nodes are, say, U11–18 and U28–37. A `-[01-18]` style
assumption silently builds a wrong `--nodelist`, which presents as jobs pending
forever with no error. Regenerate any time:

```bash
docs/gen-inventory-from-slurm.sh > conf/inventory/racks.txt   # Slurm is authoritative
python3 docs/gen-inventory.py <cluster>.xlsx > conf/inventory/racks.txt  # from a workbook
```

## 5. Step 2 — verify

```bash
bin/verify-cluster.sh --fix-hints
bin/verify-cluster.sh --deep --fix-hints     # also srun a real node
```

Checks the environment, Slurm tooling and accounting, partition, topology plugin,
GPUs per node, **inventory vs live Slurm node names**, rack sizes, group
alignment, `llmb-run` release and subcommands, `$LLMB_INSTALL` layout, image
presence, and that every workload in the matrix is installed. `--deep` confirms
the fabric interface exists, the GPU count, and node-local scratch writability.

Exit 0 only when there are no FAILs. `--fix-hints` prints the remedy for each.

### The check that matters most

If `sinfo` reports a different node-name family than your inventory, **every**
nodelist is wrong. Site documentation often carries two naming domains for the
same hardware (an OS/provisioning name and a cabling/port-map name). Slurm is
authoritative for `--nodelist`. The verifier fails hard on a total mismatch and
tells you to regenerate from Slurm.

Then dry-run — prints every command it would execute, writes no state:

```bash
bin/rack-orchestrator.sh --dry-run
```

```
DRY-RUN: env RUN_CONF_IMAGE=/raid/llmb/<image>.sqsh NCCL_SOCKET_IFNAME=<iface> \
  llmb-run submit -w microbenchmark_nccl -s nccl --dtype fp8 --scale 72 \
  --force --nodelist rack01-[11-18,28-37]
```

If those are not the commands you want run, fix `conf/` — not the scripts.

## 6. Step 3 — deploy

### Stage the container image to node-local disk

```bash
actions/file_copy.sh '<nodelist>'
```

Two-stage hierarchical copy: shared FS → one leader per rack → rack siblings. At
rack scale, pulling a multi-GB squashfs to every node straight off the shared
filesystem will saturate it. `LLMB_STAGE_IMAGE=0` opts out.

### Wire up per-node health checks

Depends on `NODE_HEALTH_DRIVER` from the interview:

```bash
# bcm
pre-post/create-action-trigger.sh        # registers actions + devicestatus==UP triggers
                                         # remove with delete-action-trigger.sh
# cron (on each node)
*/10 * * * * root /opt/llmb-bringup/actions/node_health.sh
*/5  * * * * <svc> /opt/llmb-bringup/actions/launch_job.sh
```

**Never trigger rack-scale workloads per node** — a per-node hook fires on every
node, so a rack would submit its own job N times.

### Establish the health baseline

```bash
bin/set-valid-default.sh <a fully validated node>
```

`node_health.sh` diffs every check against this baseline, so pick a node you
trust. Re-run after an intentional fleet-wide firmware or BIOS change.

### Recommended rollout

| Step | Command | Why |
|---|---|---|
| 1 | `bin/rack-orchestrator.sh --dry-run` | read the commands |
| 2 | `bin/rack-orchestrator.sh --rack <rack> -v` | one rack, verbose |
| 3 | `bin/rack-status.sh --metrics` | calibrate thresholds on real numbers |
| 4 | edit the profile floors to ~90 % of observed | §9 |
| 5 | run against one row/SU | `MAX_SUBMITS_PER_CYCLE` throttles it |
| 6 | enable the timer | whole fleet |

## 7. Automating the whole suite

The end state: **a node boots and no human touches it again unless it fails.**

### Two layers

**Per node, event-driven.** Health checks set Slurm `IDLE` or `DOWN` with a
reason, and node-scope sbatch work (GPU diagnostics) runs. Re-evaluated every
cycle, so a repaired node re-tests itself.

**Per rack, polled.** `rack-orchestrator.sh` every 5 minutes: collect verdicts,
then submit newly eligible racks. Both halves are `flock`-protected and
idempotent — overlapping runs exit 0 without submitting, so a cron misfire is
harmless.

### Enable

```bash
sudo cp systemd/llmb-bringup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now llmb-bringup.timer
systemctl list-timers llmb-bringup.timer
```

Adjust `User=` and the paths in the unit if your deploy root differs. Or cron —
see `systemd/crontab.example`:

```cron
*/5 * * * * <svc> /opt/llmb-bringup/bin/rack-orchestrator.sh   >/dev/null 2>&1
*/2 * * * * <svc> /opt/llmb-bringup/bin/llmb-collect.sh        >/dev/null 2>&1
0   7 * * * <svc> /opt/llmb-bringup/bin/status-daily-report.sh >/dev/null 2>&1
```

The extra collect entry turns verdicts around faster than the submit cycle.

### Throttles

| Setting | Default | Effect |
|---|---|---|
| `MAX_SUBMITS_PER_CYCLE` | 8 | new jobs per pass |
| `QUEUE_DEPTH_LIMIT` | 32 | stop submitting at this queue depth |
| `SUBMIT_SLEEP` | 10 | seconds between submissions |
| `MAX_RACK_JOB_HOURS` | 30 | over-running job is cancelled and failed |
| `ON_RACK_FAIL` | `drain` | drain the rack's nodes (`none` = record only) |
| `RETRY_FAILED` | 0 | do **not** retry a real failure; humans triage |
| `RETRY_INFRA_FAIL` | 1 | do retry `NODE_FAIL` / `BOOT_FAIL` / preemption |
| `MAX_ATTEMPTS` | 3 | attempts before giving up |

### What done looks like

```
rack       nodes        dcgm    nccl_single  nemo_single  nccl_multi
rack01     18/18 idle   DONE    DONE         DONE         DONE
rack03     0/18 idle    DONE    FAIL         NOT_RUN      NOT_RUN

workload           DONE     FAIL  RUNNING SUBMITTED  NOT_RUN
nccl_single         111        1        0        0        0

TO INVESTIGATE
  rack03  nccl_single  all_reduce=449.0<820,all_gather=449.0<620,...
```

### Adding a check

Append to `conf/workloads.conf` — no script changes:

```bash
workload nvbandwidth \
    runner=sbatch scope=node gate=dcgm \
    sbatch=nvbandwidth.sbatch runs=1 metric=- thresholds=-
```

Drop `jobs/nvbandwidth.sbatch` in (copy `jobs/example.sbatch`; its parse section
must `echo DONE` or `echo FAIL` last). For an llmb workload set `runner=llmb`,
`llmb_workload=`, `scope=rack|group` and thresholds.

Unknown keys and forward gate references are **fatal at startup** — a typo cannot
silently become a default.

## 8. The validation matrix

`conf/workloads.conf`. File order is gating order.

| # | workload | runner | scope | GPUs | gate |
|---|---|---|---|---|---|
| 1 | `dcgm` | sbatch | node | 1 node | — |
| 2 | `nccl_single` | llmb | rack | 1 NVLink domain | `dcgm` |
| 3 | `nemo_single` | llmb | rack | 1 NVLink domain | `nccl_single` |
| 4 | `nccl_multi` | llmb | group | N racks | `nccl_single` on all N |
| 5 | `soak` | llmb | group | N racks | `nemo_single`, `nccl_multi` — `enabled=0` |

`nccl_single` sweeps all five collectives (all_reduce, all_gather,
reduce_scatter, alltoall, sendrecv) in one job.

### What one sweep actually contains

`microbenchmark_nccl -s nccl` is **24 tests**, not five — each collective runs
several variants. On a 72-GPU GB300 rack the whole sweep is one Slurm job of
roughly 26 minutes. The six `all_reduce` variants are
`NCCL_NVLS_ENABLE=[0,1]` × `-G=[None,2,4]`, and **the two halves are far apart**:

```
NVLS off :  704.17   696.08   696.27     GB/s busbw
NVLS on  :  914.98   916.60   916.84
```

NVLS is worth roughly **+31 %**. This matters for scoring: the GB300 all_reduce
floor is 820, so a parser that reads the *first* block rather than the best would
report ~700 and produce a **false FAIL on a healthy rack**.

`nccl_peak_busbw` in `lib/results.sh`/`lib/llmb.sh` therefore takes the peak
across every sweep file for a collective, every message size, and both the
in-place and out-of-place `busbw` columns — so the NVLS-on block wins. If you
replace the parser, preserve that: **score a collective on its best block, not
its first.** `tests/lint.sh` and `test_unit_nccl_busbw_both_layouts` cover the
column-layout half of this.

Groups are formed from the inventory in order, so with a tidy inventory they do
not straddle a row or scalable unit. Partial trailing groups are dropped: 3 racks
is not a 4-rack test. `MULTI_RACKS_PER_JOB` sets the size.

## 9. Platform profiles and thresholds

`conf/profiles/<name>.conf` supplies rack geometry and NCCL bandwidth floors;
`conf/cluster.conf` sources the one the interview selected, and
`conf/workloads.conf` references `$NCCL_FLOOR_*`. Shipped: `generic`,
`gb300-nvl72`, `gb200-nvl72`, `vr200-nvl144`, `hgx-8gpu`.

**An empty floor means no floor.** `generic` and the less-characterised profiles
ship with floors unset on purpose: a workload then passes on completion, and
marginal racks are caught only by the fleet-relative gate. That is the honest
default for a platform whose fabric you have not measured.

Calibrate:

```bash
bin/rack-status.sh --metrics
grep -h '^m_' state/racks/*/nccl_single.state | sort | uniq -c
```

Set the floors to roughly 90 % of what healthy racks actually achieve, in your
profile.

### The `gb300-nvl72` floors are measured, not guessed

A full sweep on one healthy 72-GPU rack (job 65828, COMPLETED in 26m15s,
`#wrong=0` on all 24 tests) against the shipped floors:

| Collective | Profile floor | Measured | Margin |
|---|---|---|---|
| all_reduce | 820 | **916.84** | +11.8 % |
| reduce_scatter | 640 | **708.30** | +10.7 % |
| alltoall | 620 | **690.72** | +11.4 % |
| sendrecv | 625 | **686.84** | +9.9 % |
| all_gather | 620 | **646.78** | +4.3 % |

All five clear their floor, and the margins are tight enough (4–12 %) that the
floors are doing real work rather than passing everything. `all_gather` has the
least headroom — expect it to be the first collective to flag a marginal rack.
`PROFILE_GPUS_PER_NODE=4` × `PROFILE_NODES_PER_RACK=18` = 72 matched the live
rack exactly. Full detail and method in
[VALIDATION-NscaleTX-2026-07-29.md](VALIDATION-NscaleTX-2026-07-29.md) §3.

These are still **field observations from one fleet, not vendor specifications**.
They are a defensible starting point for GB300 NVL72; confirm on your first few
racks. Every other profile ships uncalibrated on purpose.

The fleet-relative gate flags any rack more than `OUTLIER_FRAC` (5 %) below the
running mean of already-passing racks, once `OUTLIER_MIN_SAMPLES` (8) exist.
Absolute floors catch gross failures; the relative gate catches the marginal rack
a fixed floor waves through.

## 10. Day-2 operations

```bash
bin/rack-status.sh                 # matrix + TO INVESTIGATE
bin/rack-status.sh --metrics       # numbers
bin/rack-status.sh --pending       # what is blocked, and by what
bin/rack-status.sh --rack <rack>
bin/status-check.sh                # per-node, dshbak-grouped
bin/status-daily-report.sh         # CSV, one column per collective
bin/llmb-collect.sh                # collection pass only
bin/watch-rack.sh '<nodelist>'
bin/node-health-refresh.sh '<nodelist>'
```

### Re-run a rack after a repair

```bash
scontrol update nodename='<rack nodelist>' state=RESUME
rm state/racks/<rack>/nccl_single.state
rm -f results/<rack>-*/nccl_single.txt
bin/rack-orchestrator.sh --rack <rack> -v
```

### After a hardware swap

```bash
bin/single-node-purge.sh <node>        # clear that node's results
bin/node-health-refresh.sh <node>      # force a health re-check
```

State files are flat `KEY=VALUE` on purpose — greppable and hand-editable on a
bring-up call. Each carries `logdir=` pointing at the raw llmb output.

## 11. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `no site configuration` | interview not run | `bin/interview.sh` |
| `llmb-run not on PATH` | venv not activated | set `LLMB_VENV` |
| `cannot be pinned` | older `llmb-run`, no `submit` | upgrade, or `AAT_ALLOW_UNPINNED=1` |
| `no TFLOPS/GPU reported` | no `llmb-run jobs` subcommand | upgrade, or `metric=-` |
| Jobs pend forever, no error | wrong node names → bogus `--nodelist` | `bin/verify-cluster.sh`; regenerate inventory from Slurm |
| `Requested topology configuration is not available` | `--nodelist` under `topology/block` | `SLURM_TOPOLOGY=block` |
| Rack never submits | one node not idle | `bin/rack-status.sh --pending`; `sinfo -R` |
| `COMPLETED but no NCCL result dir` | wrong `LLMB_INSTALL` | check the experiments path |
| Everything `unknown to slurm`, endless retries | `sacct` unavailable | fix Slurm accounting |
| All racks fail thresholds at once | uncalibrated floors | §9 |
| `refusing to run as root` | wrong user | run as the service user, or `ALLOW_ROOT=1` |
| Container pull slow every job | image not staged | `actions/file_copy.sh` |
| `Invalid scale` / submit rejected outright | rack GPU count not in the upstream scale whitelist | keep `scale_flag=force`; never patch `metadata.yaml` (§3) |
| `ucp_ep_create … Destination is unreachable`, every rank `Killed` | `UCX_TLS` restricts transports the container does not have | unset it — see §11.1 |
| `Detected mixed local CollNet device counts across ranks (min 3, max 4)` | `NCCL_IB_HCA` pinned fleet-wide, but a tray has fewer rails | unset it and let each rank auto-detect — §11.1 |
| Healthy rack FAILs all_reduce at ~700 GB/s | scored the NVLS-off block instead of the best | parser must take the peak across blocks (§8) |

Logs: `log/aat.log`. Verdicts: `state/racks/<rack>/<workload>.state`. Drain
reasons: `sinfo -R`.

### 11.1 Environment variables you must not set

Confirmed the hard way on a live GB300 cluster. All three look like reasonable
fabric tuning and all three break rack-scale jobs. This repo deliberately sets
**none** of them — do not add them to `LLMB_EXTRA_ENV`.

| Variable | What happens if you set it |
|---|---|
| `UCX_TLS` (e.g. `^tcp`) | **Fatal.** The llmb/NeMo container exposes only tcp/IPoIB — no mlx5 verbs — so forbidding tcp leaves UCX with no transport at all: `ucp_ep_create … Destination is unreachable`, every rank `Killed`. |
| `NCCL_IB_HCA` | **Fatal on any asymmetric rack.** Rail counts are a *per-node* fact. Pinning a list derived from one node's probe makes NCCL open a device that does not exist on another tray → `Detected mixed local CollNet device counts across ranks` and the job aborts. |
| `UCX_NET_DEVICES` | Same failure class as the two above, for the same reason. |

The rule behind all three: **probe results from one node are not fleet facts.**
Let each rank auto-detect its own devices.

`NCCL_SOCKET_IFNAME` is the exception and *is* set from `cluster.conf` — it names
the bootstrap interface, not a device list, and the interview probes it on a real
compute node (§4).

#### Rail asymmetry is real, and tolerable

On the validated cluster two trays carried 3 of 4 compute rails (verified via
sysfs: ACTIVE + InfiniBand + 800G, bond excluded). Unpinned, the llmb container
path completed the full sweep anyway; a host-mpirun path did not. So asymmetry is
not automatically a bring-up blocker — but it is exactly the condition that turns
a pinned `NCCL_IB_HCA` into an aborted job, which is why the table above is not
optional advice.
